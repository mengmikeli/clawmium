# /auto mode spike — first autonomous navigation + extraction boundary

Date: 2026-02-17
Scope: `src/auto/`, `src/cli/repl.ts`, `src/llm/`

## What was built

Three things in one session:

1. **CityServe SPA auth fix** — post-login race condition (500ms settle delay + interceptor clear) and `/api/account` added to skip list. Two compounding bugs: stale interceptor data hijacks page processing even if DOM loads correctly.

2. **`/auto` mode** — autonomous browsing loop. `/auto <goal>` drives the browser: interpret → planAutoAction → executeChoice → loop. Stops on: data found, step limit (10), loop detection, consecutive errors, abort signal, or `ask_human`. 63 unit tests + E2E against CityServe.

3. **Choice execution extraction** — `executeChoice()` pulled from inline REPL code into `src/auto/executor.ts`. Both human choice selection and auto mode use the same function. First concrete step of the REPL refactor proposed in `2026-02-17-4.md`.

## Learnings

### 1. Extraction boundary discovery: the spike justified the refactor

The `/auto` spike immediately needed `executeChoice()` shared between human and auto paths. This wasn't planned — it fell out of the implementation. The REPL risk review (2026-02-17-4.md) proposed extracting navigation transactions as Phase 1; `/auto` forced one concrete extraction (choice execution) before the systematic refactor.

**Pattern:** Feature spikes are the best refactoring scouts. They find the real extraction boundaries because they *need* them, not because a review *predicted* them. The risk review was directionally correct (duplicate navigation logic is the problem) but the `/auto` spike found the specific seam.

**Implication for REPL refactor:** The remaining Phase 1 extraction (`navigateAndProcess()` for `/goto`, `/home`, `/demo`) is now higher-confidence. One extraction already worked; the pattern is proven. But the right trigger is the next feature that needs it, not a cleanup sprint.

### 2. `interpretPageOnly()` duplicates `_processCurrentPage()` — and that's a design signal

`interpretPageOnly()` is ~100 lines that closely mirror `_processCurrentPage()` minus rendering. The duplication exists because the two functions have different contracts:
- `_processCurrentPage()`: interpret + render + prompt (side effects everywhere)
- `interpretPageOnly()`: interpret + return (pure-ish, no render)

The auto runner needed the pure version. The REPL has the effectful version. Both share the same interpret-extract-fallback logic.

**Lesson:** When you need a "pure" version of an effectful function, the effectful function was probably doing too much. The right factoring is: pure core (interpret) + effectful shell (render). This matches Principle #2 from the meta-learnings: separate mechanism from semantics, and here, separate *computation* from *presentation*.

**Future:** Extract `interpretPage()` as pure function, have both `_processCurrentPage()` and `interpretPageOnly()` call it. This is Phase 3 of the REPL refactor (split non-command executors) — but the seam is already visible.

### 3. `planAutoAction()` is a new LLM method, not a reuse of `planAction()`

The original `planAction()` (from day one, never called in production) had a different contract: it received a `PageInterpretation` and a `ConversationContext` and returned an `AgentAction` (type + selector + reason). The new `planAutoAction()` receives a formatted string context (goal, page summary, numbered choices, history, visited URLs) and returns an `AutoPlanResult` (choiceIndex or type + reasoning).

**Why the split:** `planAction()` was designed before the choice system existed. It operated on raw selectors and page structure. `planAutoAction()` operates on numbered choices — the same abstraction the human uses. This makes the prompt simpler, the output more constrained, and loop detection possible (the "VISITED" section warns the LLM away from repeated URLs).

**Principle restated:** Dead code (`planAction()`) didn't just mark an architectural fork (meta-learnings Principle #4) — it marked a *wrong abstraction level*. The right level for autonomous planning is choices, not selectors. The human path already discovered this; the auto path just adopted it.

### 4. The auto runner is a finite state machine, not a loop

The `runAuto()` function looks like a for-loop but behaves as a state machine with these states:
- **Sync** (browser check, recovery on failure)
- **Interpret** (page understanding)
- **Auth gate** (login detected → hand off → re-enter interpret)
- **Data gate** (data found → extract → done)
- **Plan** (LLM picks action)
- **Execute** (choice execution → back to sync)
- **Terminal** (completed | stuck | cancelled | step_limit | login_failed)

Transitions: consecutive error counter gates re-entry; URL visit counter gates loop detection; abort signal gates cancellation.

**Why this matters:** The for-loop implementation works but makes it hard to add states (e.g., "confirm with human before risky navigation"). The state machine shape suggests the eventual `/auto` v2 should be explicit states + transitions, not a monolithic loop. But for the spike, the loop is correct — premature FSM abstraction would have slowed the experiment.

### 5. E2E test harness: `interpretPage` as the integration seam

The E2E test (`__test__auto_e2e.ts`) wires real Playwright + real LLM but replaces `interpretPage` with a custom function that:
- Calls `detectLoginPage()` and `detectInteractiveForms()` directly
- Extracts content via `nav.extractContent()`
- Checks interceptor for API data (with the same skip patterns as production)
- Calls `llm.interpret()` with the same prompt construction
- **Nulls out `dataFound` from LLM** to prevent premature extraction from dashboard account data

The last point is critical: the LLM sometimes reports "data found" when it sees account details on the dashboard page, before reaching the actual water bill page. The E2E test learned this the hard way — the LLM's `dataFound` is unreliable for goal completion; only intercepted `/api/water-bill` data is the real signal.

**Generalization:** When the LLM and the interceptor disagree about "is this the target data?", trust the interceptor. The interceptor sees the actual API response; the LLM sees a summary. For structured data extraction, mechanical signals (URL pattern, response shape) beat semantic signals (LLM judgment).

### 6. CityServe auth bug was a pattern violation, not a novel bug

The auth fix (interceptor clear + settle delay) matches the exact pattern already used by `/goto`, `/home`, `/demo`, and `/refresh`. The post-auth path was missing it because auth was implemented before the pattern was established.

**Lesson:** When a resilience pattern exists in 4 of 5 navigation paths, the 5th path probably needs it too. This is exactly the problem the REPL risk review identified (§3: "duplicate navigation transaction logic — any bug fix must be manually propagated"). The `executeChoice()` extraction partially addresses this; the full `navigateAndProcess()` extraction would prevent it entirely.

## Top takeaway

**Feature spikes find better extraction boundaries than code reviews.** The REPL risk review correctly identified the problem (duplicate navigation logic); the `/auto` spike found the specific seam (`executeChoice()`). Reviews predict where to look. Spikes prove where to cut.
