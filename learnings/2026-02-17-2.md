# Session, Crawl, Memory — three layers of browsing state

## Preamble

A debugging session revealed that cross-domain `/goto` destroys in-session navigation history — `/back`, `/stack`, and `/history` all lose the previous domain's pages. The investigation started as a bug fix but uncovered a deeper question: what are the layers of state in an agent-first browser, and what belongs in each?

The conversation produced three things: (1) a concrete fix (the "stash" model for preserving session history), (2) a three-layer architecture for browsing state, and (3) a vision for persistent crawl artifacts that mirrors how humans manage browser tabs.

---

## 1. The browser tab analogy holds — and reveals the layers

The debugging session surfaced a mapping between traditional browser concepts and Clawmium's model:

| Browser | Clawmium | Layer |
|---------|----------|-------|
| Open tab | Stashed crawl | Session |
| Close tab (dead end) | Prune crawl | Session |
| Tab hell (30+ open) | Stash bloat | Session |
| Back button (cross-tab) | `/back` across stash | Session |
| Bookmarks / saved pages | Persisted crawl folders | Persistence |
| Edge Journeys / Arc Spaces | LLM-curated crawl memory | Memory |

The analogy isn't decorative — it's structurally load-bearing. Every UX problem in browser tab management (accumulation, staleness, context loss, semantic grouping) has an exact counterpart in crawl management. The solutions map too: immediate pruning for dead ends, stacking for context preservation, LLM curation for long-term organization.

**The key insight**: browsers solve these problems at the UI layer (tab bar, tab groups, auto-discard). Clawmium should solve them at the file system layer — because files are the interface both humans and LLMs can work with.

---

## 2. Three layers, cleanly separated

The discussion converged on three distinct layers of browsing state:

| Layer | Concept | Lifetime | What it captures |
|-------|---------|----------|-----------------|
| **Session** | Resume where you left off | Ephemeral — one run to the next | Active crawl + stash + REPL state. Gone on `--new` |
| **Crawl** | Semantic unit of browsing intent | Persistent — saved to disk | Tree of pages with summaries, navigation paths, LLM interpretations |
| **Memory** | Long-term recall across sessions | Permanent | LLM-organized knowledge artifacts built from crawls |

**Session** is about not losing context mid-run. The stash is a session concept — it holds previous crawls in memory so `/back` works across domains. On resume, the stash comes back. On `--new`, it's gone. The `SessionEnvelope` captures this layer.

**Crawl** is the semantic building block. Each crawl represents a unit of browsing intent ("reading about AI on HN", "checking my water bill"). Crawls are the durable artifacts — they survive across sessions, they're saved to disk, they're the units you query when asking "what did I read last week?" The crawl is persistent because it carries meaning.

**Memory** is derived from crawls, not built independently. The LLM reads crawl artifacts and organizes them — summarizing, linking related crawls, pruning stale ones. Memory is the layer where "I read a Stratechery article about Microsoft and AI" lives, even if the session that produced it is long gone.

**Why the separation matters**: Before this discussion, the codebase conflated session and persistence. `clearCrawl()` both saved to disk (persistence) and destroyed in-memory state (session) in the same call. The fix (stash model) works because it operates entirely in the session layer without changing persistence. The future persistence refactor (crawl folders) works because it operates entirely in the persistence layer without changing session mechanics.

---

## 3. Crawls are knowledge artifacts, not log files

The current persistence model treats crawls as log files: one flat `.md` per crawl, containing a tree dump and node summaries. The vision is fundamentally different — crawls should persist as **structured knowledge artifacts**:

```
~/clm/crawls/
  hacker-news-ai-articles/           # Named folder per crawl
    README.md                         # LLM-generated front page
    hn-front-page.md                  # Per-page content/summary
    courtsdesk-article.md
    xmpp-server.md

  stratechery-microsoft-ai/
    README.md
    microsoft-software-survival.md
    ai-and-the-big-five.md
```

The `README.md` is the crawl's "front page" — LLM-generated to provide a summary of what was explored, key findings, open TODOs, and a directory of the individual page files. Each page file contains the LLM's content summary for that page.

This makes crawls:
- **Browseable by humans** — `ls ~/clm/crawls/` shows your browsing history as named folders. `cat README.md` tells you what a crawl was about.
- **Queryable by LLMs** — an agent can read READMEs across crawls to answer "what did I read about AI last week?"
- **Composable** — crawl folders can be merged, split, or reorganized at the file system level.

The file system is the storage layer. The LLM is the librarian.

---

## 4. Transient intent and the pruning problem

Not all crawls deserve persistence. A cross-domain `/goto` that hits a paywall and immediately `/back`s creates a 1-node crawl with no content — the browsing equivalent of opening a tab, seeing it's useless, and closing it.

In a browser, the user closes bad tabs manually. In Clawmium, the LLM can judge this at persist time. Three decisions:

- **Prune**: Dead-end crawl (1 node, no summary, paywall/error). Discard — don't promote to a persistent folder.
- **Preserve**: Standalone topic with real content. Gets its own folder with README + per-page files.
- **Merge**: Two crawls are semantically related (e.g., HN article links to Stratechery follow-up on the same topic). Combine into one folder; LLM rewrites the README to reflect the merged narrative.

This mirrors the browser tab lifecycle exactly: prune = close bad tab, preserve = bookmark, merge = tab grouping. But instead of requiring manual human judgment at scale (which leads to tab hell), the LLM handles curation automatically.

**The timing matters**: pruning happens at the transition from session to persistence. During the session, even a 1-node crawl stays in the stash (the user might `/back` to it). Only when promoting to a durable artifact does the LLM judge signal vs noise.

---

## 5. Implementation phasing follows the layers

The three-layer model naturally sequences into implementation phases:

1. **Session layer (now)**: Crawl stash — `pushStash()`/`popStash()` on CrawlManager, unified `/history`, `SessionEnvelope` v3 with stash serialization. Pure in-memory session state management.

2. **Persistence layer (next)**: Crawl folders — replace flat `.md` with named directories, per-page files, LLM-generated README. This is a persistence format change; session mechanics are untouched.

3. **Memory layer (future)**: LLM curation at persist time — prune/preserve/merge decisions, cross-crawl linking, long-term recall. This requires both the folder structure (to write into) and the stash (to read from).

Each phase builds on the previous without requiring changes to it. The stash doesn't need to know about folders. The folders don't need to know about LLM curation. But curation needs both stash (as input) and folders (as output).

---

## Coda

The session started as "why does `/history` lose my HN pages after `/goto stratechery.com`?" — a concrete bug with a concrete fix. But the fix required asking "what is the stash?" which required asking "what is a session vs a crawl?" which required asking "what gets persisted and why?"

The answer — three layers (session/crawl/memory), each with different lifetimes and different owners — turned out to be latent in the codebase. The `SessionEnvelope` was already a session concept. The crawl `.md` files were already a persistence concept. The LLM summaries on crawl nodes were already a memory concept. The layers existed; they just weren't named or separated.

Naming them changes what you can build. "The stash is session-layer" means you can add it without touching persistence. "Crawls are knowledge artifacts" means persistence can evolve independently. "Memory is LLM-curated" means curation logic doesn't need to be baked into data structures. The same principle from learning 17-1 #2 (separate facts from judgment) applies here — but between architectural layers instead of between code and LLM.

The persistence layer will evolve crawls from flat `.md` files into structured knowledge artifacts:

```
~/clm/crawls/
  hacker-news-ai-articles/           # Named folder per crawl
    README.md                         # LLM-generated front page: summary, TODOs, directory
    hn-front-page.md                  # Per-page content/summary
    courtsdesk-article.md
    xmpp-server.md

  stratechery-microsoft-ai/
    README.md
    microsoft-software-survival.md
    ai-and-the-big-five.md
```

**LLM-assisted persist-time decisions** — when promoting crawls from session stash to durable artifacts:
- **Prune**: Dead-end crawls (paywall, error, 1-node no content) -> discard, don't persist
- **Preserve**: Standalone topic crawl -> gets its own folder with README + per-page files
- **Merge**: Semantically related crawls (e.g., HN article -> Stratechery follow-up) -> combine into one folder, LLM rewrites README

This mirrors browser tab management: prune = close bad tab, preserve = bookmark, merge = tab grouping. The file system is the storage layer — greppable, readable, versionable. The LLM is the librarian.
