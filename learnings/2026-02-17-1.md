# Meta-learnings: Five principles from the Feb 16-17 build sprint

## Preamble

Five learnings files span Feb 16-17: architecture alignment (16-0), crawls design review (16-1), form detection wiring (16-2), crawl command layer (16-3), and session persistence + polish (17-0). Together they contain 27 individual learnings — the most architecturally dense stretch of the project. The sequence was: stop building and review the architecture → design the crawl system → wire real-site form detection → build the command layer → make sessions persistent and polish the main view.

Many of the 27 are the same insight wearing different hats. The crawls design review discovers "record facts, defer interpretation" as a data modeling principle. Session persistence rediscovers it as "trust the LLM at the semantic layer." The architecture alignment discovers it as "the intelligence-location question." They're all asking the same question — *where does judgment live?* — in different contexts.

This file distills the five principles that appeared most frequently, proved most consequential, and generalize most clearly beyond this project.

---

## 1. Stop building and align — it's higher leverage than another feature

**Source:** 16-0 #6 ("alignment sessions produce more value per hour than feature sessions")

Three days of building produced a working browser with real-site support, HN extraction, form detection, goal tracking, and dual LLM providers. It also produced 8 open architectural questions that nobody had explicitly decided: Is Clawmium infrastructure or an autonomous agent? Where does intelligence live? What's the navigation model? How should it be consumed? What ships next?

One alignment session — no code written — resolved 7 of the 8. The `planAction()` discovery alone (implemented in both providers, tested, called from zero production paths) revealed that the project had unconsciously forked between "human drives agent" and "agent drives itself" without anyone picking which was primary. That single observation reframed the entire TODO.

**The trap:** shipping feels productive. Alignment feels like talking. But decisions-as-debt compounds silently. Every feature built on top of unresolved architectural ambiguity might need to be rebuilt once the ambiguity is resolved. The 16-0 session wrote zero lines of code, and it was arguably the most productive session of the sprint — because every subsequent session (16-1 through 17-0) could build on resolved foundations instead of guessing.

**Generalization:** Past a certain codebase size — maybe 1-2 kLOC, or maybe the threshold is "more than one person's mental model" — the ratio of alignment to building should increase, not stay constant. The question "are we building the right thing?" becomes more expensive to answer wrong as the codebase grows, and cheaper to answer right if you stop and ask explicitly.

## 2. Separate the mechanical layer (facts) from the semantic layer (judgment)

**Sources:** 16-1 #2 ("don't hardcode rules"), 16-1 #3 ("simple infra + LLM semantics = safe refactoring"), 16-1 #4 ("record facts, defer interpretation"), 17-0 #3 ("trust the LLM at the semantic layer")

This is the most frequently rediscovered principle in the sprint — it appeared 4 times across 2 files, each time wearing a different hat.

**The pattern:** The crawl tree records `reachedBy: 'goto'` (fact). Whether that constitutes a "context switch" is interpretation. The tree stores URLs and timestamps. Whether a crawl should be named "checking water bill" or split into two crawls is judgment. The `CrawlNode` stores a `summary` field populated by the LLM. Whether that summary means the user has achieved their goal is inference.

Facts are cheap, stable, and don't change as your understanding improves. Judgments are expensive, context-dependent, and improve with better prompts.

**Why it kept being rediscovered:** Each new feature hit the same boundary between "what should the data structure decide?" and "what should the LLM decide?" — but the question looked different every time:

- **Design review (16-1):** Should burst detection (3 URLs in 30s) auto-create a project crawl? Answer: no — that's a judgment call disguised as a heuristic. Record the timestamps, let the LLM judge intent continuity.
- **Design review (16-1):** Should the tree classify edges as "related navigation" vs "context switch"? Answer: no — record `reachedBy` as a mechanical fact, let the LLM interpret when needed.
- **Design review (16-1):** Should there be a project/scratch mode distinction? Answer: no — all crawls are structurally identical. Whether a crawl is "important" is a semantic judgment, not a data model flag.
- **Session persistence (17-0):** Where should interpretations live? Answer: as metadata on the tree node (a fact: "this is what the LLM said about this page"), not as tree structure (which would bake semantic decisions into the topology).

The answer was always the same. The question just looked different each time because each feature presented a new surface where the boundary between mechanism and meaning had to be drawn.

**Generalization:** In any LLM-augmented system, push all semantic judgment to the LLM layer and keep the infrastructure layer as a dumb fact recorder. This makes the hard-to-change parts (data structures, persistence formats, serialization) stable, and the easy-to-change parts (prompts, heuristics, classification logic) soft. When you want to improve the system's judgment, you change prompts — not schemas.

## 3. Simple foundations don't resist new layers — they absorb them

**Sources:** 17-0 #1 ("trail representations compound"), 17-0 #2 ("simple core mechanics make compounding safe"), 16-3 #1 ("bottom-up phasing pays off at the command layer")

**The story:** In four days, the project went through four trail representations:

1. `pageStack` / `forwardStack` (Feb 14) — linear back/forward navigation
2. Crawl tree (Feb 16) — branching structure with URL deduplication
3. Cursor history on CrawlManager (Feb 17) — linear projection of the tree for back/forward/jump
4. `pageStack` / `forwardStack` eliminated (Feb 17) — the tree absorbed their role entirely

Each emerged from an immediate need. Each worked. Each got subsumed by the next. The tree survived — and absorbed the stacks — because its operations are trivial: create node, find by URL, attach to parent, store metadata, walk ancestors. No business logic. No decision-making. Four operations, each doing exactly one thing.

When cursor history needed to be bolted on, the tree's simplicity meant no restructuring was required — just 8 new methods operating on a `CursorEntry[]` array alongside the existing tree. When `pageStack` / `forwardStack` needed to be eliminated, the tree could absorb that responsibility because it was already tracking the same information with more structure. When Phase 4 (16-3) built the command layer (`/crawl list|load|rename|end|info`), it was almost entirely glue code — `peekCrawl()` was the only genuinely new logic, because all the machinery already existed.

**The counterexample (implicit):** The original crawls design (16-1) proposed burst detection, project/scratch modes, and `detachSubtree`/`attachSubtree` for LLM reorganization. If any of those had been built into the tree's core operations, adding cursor history would have required restructuring — because cursor history doesn't care about burst boundaries or project classifications. Every piece of business logic in a data structure is a constraint that future layers must negotiate with.

**Generalization:** If your data structures have no business logic, you can stack representations on top of them without fear. The moment a data structure starts making decisions, new layers need to negotiate with it instead of building on it. Simplicity isn't just aesthetic preference — it's structural load-bearing capacity. The question to ask is: "if I need to bolt something new onto this in two weeks, will I need to restructure it?" If the answer is "no, because there's nothing to conflict with," the foundation is right.

## 4. Dead code tells you where your architecture forked

**Source:** 16-0 #1 ("dead code is a signal, not just debt")

**The story:** `planAction()` — a method on the `LLMProvider` interface, implemented in both OpenAI and Anthropic providers, tested in the LLM test file, called from zero production code paths. It existed from the earliest implementation, designed to let the agent autonomously decide the next navigation action based on a page interpretation.

Standard instinct: "we'll use it later" or "clean it up." But the right question was: *why is this never called?*

The answer: the REPL loop replaced it. The human makes every navigation decision by pressing a number. The function designed for agent autonomy was made redundant by human-in-the-loop design — and nobody noticed, because both the autonomous interface and the human-driven REPL were built as part of the same "agent-first browser" vision. The code was perfectly functional. The architecture had silently forked between two different meanings of "agent-first," and `planAction()` was the bookmark for the fork.

**Why this is more than "delete dead code":** Dead code from abandoned features is routine cleanup. Dead code from *never-used planned features* is different — it's evidence that the plan and the reality diverged, and the divergence was never acknowledged. The fix isn't deletion; it's asking "why was this never called?" and answering honestly. In this case, the answer ("we designed for autonomous navigation but built human-in-the-loop interaction") triggered the entire architecture alignment session that became the most productive session of the sprint.

**Generalization:** When you find planned-but-unused code — not deprecated code, not feature-flagged code, but code that was written as part of the original design and never wired in — it's a bookmark for an unresolved architectural decision. The question "why isn't this called?" is often more valuable than the code itself. The code is easy to delete. The architectural fork it reveals might be shaping every feature you build.

## 5. When two subsystems seem to overlap, look for the feedback loop

**Sources:** 16-1 #1 ("intent and structure are a feedback loop, not competing systems"), 16-1 #5 ("design reviews that surface feedback loops > missing fields")

**The story:** `GoalContext` (Phase 5 addition — tracks intent: baseGoal, activeIntent, breadcrumb trail) and the crawl tree (Phase 2-3 — tracks navigation structure: URLs, parent-child edges, timestamps) both seemed to track "where the user has been." `GoalContext.breadcrumb` was a flat 3-element sliding window; the tree captured the same path more richly. The instinct was to merge them or pick one.

The insight: they're a feedback loop, not competing systems.

```
GoalContext (intent: why am I browsing, what am I looking for)
    ↓ drives
Crawl tree (structure: what did I find, how did I get there)
    ↓ feeds back into
GoalContext (enriched: intent + structural context for better LLM prompts)
```

Intent drives navigation choices. Navigation creates tree structure. Tree structure (via `formatAncestorContext()`) enriches the LLM prompt with path history. The enriched prompt produces better interpretations. Better interpretations update GoalContext. Neither system is primary. Both are necessary at different points in the cycle.

**What this resolved:** Three design concerns collapsed once the loop was recognized:

1. **GoalContext ↔ crawl overlap** — not overlap, but two phases of a cycle. GoalContext is the intent half; the tree is the structure half.
2. **Burst detection** — became unnecessary. Intent signals from GoalContext (e.g., baseGoal changed after `/goto` to an external domain) could drive crawl lifecycle decisions directly, without timer-based heuristics.
3. **Project/scratch mode** — became unnecessary. Whether a crawl is "important" is a judgment call that the LLM can make using GoalContext + tree structure as inputs, not a mode flag set at creation time.

**Generalization:** "These two things seem to do the same job" is often wrong. Before merging or eliminating, check whether they're inputs and outputs to each other. A system that tracks intent and a system that tracks structure *look* redundant when viewed statically, but they're complementary when viewed as a cycle. The test: does A's output improve B's input? Does B's output improve A's input? If both answers are yes, you have a feedback loop, and eliminating either half degrades the whole system.

## Coda

These five principles share a common theme: **where to put intelligence and where to put mechanism** — and how to keep them cleanly separated.

*Stop and align* (1) is about recognizing that architectural decisions are a form of intelligence that can't be deferred to code. *Separate facts from judgment* (2) is the concrete engineering version: mechanism records, intelligence interprets. *Simple foundations absorb new layers* (3) is what happens when mechanism stays simple — it becomes load-bearing infrastructure that intelligence can build on without friction. *Dead code marks architectural forks* (4) is what happens when the separation breaks down — planned intelligence (autonomous navigation) and actual mechanism (human-driven REPL) diverge silently. *Look for feedback loops* (5) is what happens when intelligence and mechanism are correctly coupled — they amplify each other instead of competing.

The project's core thesis — "browsers should be built for agents first, and render pixels only when you ask" — is itself an instance of this separation. Rendering is mechanism. Understanding is intelligence. The traditional browser fuses them. Clawmium separates them. And the lessons from building Clawmium keep rediscovering that the same separation applies at every layer of the system.
