# REPL Risk Review + Refactor Plan (Phase Proposal)

Date: 2026-02-17
Scope: `src/cli/repl.ts`

## Why this review

The current REPL implementation is functionally strong and resilient, but it has reached a complexity level where feature velocity and safety will degrade unless responsibilities are separated.

This write-up captures:
1. Risk assessment of the current REPL architecture
2. Root causes of complexity
3. A comprehensive, phased refactor plan with success criteria

## Current strengths (keep these)

- Strong resilience primitives (`syncBrowser()`, recovery fallback, timeout wrappers)
- Correct state model principles (`state.currentUrl` as source of truth)
- Practical UX handling (stale choices, context hints, auth handoff, crawl stash)
- Good integration across browser/navigation/LLM/crawl/session subsystems

The target is **not** redesigning behavior; it is preserving behavior while reducing coupling.

## Risk assessment (detailed)

### 1) Responsibility concentration in one control path

`handleInput()` currently owns:
- command parsing
- command execution
- navigation orchestration
- choice execution
- free-text follow-up LLM flow
- rendering/prompt lifecycle

This centralization increases regression risk for every new command and every small feature change.

### 2) Size and branching complexity

Objective indicators from the codebase:
- `src/cli/repl.ts`: **1856 lines**
- Command switch branches (`case "..."`): **23**
- `rl.prompt()` calls: **58**

Interpretation: command paths and prompt lifecycle are heavily duplicated and easy to desynchronize.

### 3) Duplicate navigation transaction logic

Near-identical navigate-and-process sequences appear in multiple branches (`/goto`, `/home`, `/demo`, choice navigation):
- sync browser
- truncate forward cursor
- clear interceptor
- set `pendingReachedBy`
- perform `nav.goto(...)`
- update `state.currentUrl`
- short wait
- `processCurrentPage()`

Any bug fix in this sequence must be manually propagated to multiple places.

### 4) Hidden invariants are distributed

Correctness depends on many rules being followed everywhere:
- `state.currentUrl` update discipline
- when `pendingReachedBy` is set/consumed
- cursor forward truncation on new navigation
- stash push/pop behavior across domains

These invariants are valid, but currently enforced by convention, not by a single abstraction boundary.

### 5) Render and domain logic are interleaved

Rendering side-effects (`render.*`, `rl.prompt()`) are interwoven with state mutation and navigation side-effects. This makes local refactors harder to reason about and test.

## Root cause summary

Primary root cause: **orchestration logic accumulated in a monolithic REPL class without extraction boundaries**.

Secondary root causes:
- command-per-branch growth over time
- no unified action result contract for prompting
- no dedicated “navigation transaction” abstraction

## Comprehensive refactor plan

Design goal: preserve all current user-visible behavior while reducing coupling and duplicate orchestration code.

---

### Phase 0 — Safety net first

Add focused tests around the highest-risk REPL flows before structural changes:
- `/goto` external vs relative URL handling
- `/home` set/clear/navigate behavior
- `/demo` navigation path
- numbered choice navigation behavior
- stash pop behavior on `/back` across domains
- `/history N` jump behavior (active + stashed crawls)

Output: confidence baseline for no-regression refactor.

---

### Phase 1 — Extract navigation transaction (highest ROI)

Introduce a single internal operation (e.g., `navigateAndProcess(...)`) that owns:
- pre-navigation sync and cursor truncation policy
- interceptor clear
- `pendingReachedBy` assignment
- `nav.goto()` with error normalization
- `state.currentUrl` update
- optional post-nav settle delay
- `processCurrentPage()` dispatch

Migrate `/goto`, `/home`, `/demo`, and choice URL/selector navigation to this operation.

Expected outcome:
- eliminate duplicated navigation logic
- centralize navigation invariants in one place

---

### Phase 2 — Command handler extraction

Replace large switch body with dispatch map + handlers.

Proposed module split:
- `src/cli/commands/navigation.ts` (`show`, `hide`, `goto`, `home`, `refresh`, `demo`)
- `src/cli/commands/session.ts` (`save`, `quit`, `clear`)
- `src/cli/commands/crawl.ts` (`tree`, `history`, `stack`, `crawl ...`)
- `src/cli/commands/system.ts` (`help`, `url`, `login`)

`handleInput()` becomes router-only.

Expected outcome:
- simpler local reasoning
- smaller files with cohesive responsibilities

---

### Phase 3 — Split non-command input executors

Extract:
- numbered choice execution (including fill plans and stale-choice confirmation)
- free-text follow-up interpretation flow

Proposed modules:
- `src/cli/executors/choiceExecutor.ts`
- `src/cli/executors/followupExecutor.ts`

Expected outcome:
- isolate high-branching logic away from slash-command code
- easier targeted tests per executor

---

### Phase 4 — Session/crawl coordination boundary

Introduce a small coordinator to encapsulate:
- stash + restore transitions
- save/load sidecar + crawl markdown persistence orchestration
- state restoration from node metadata

This reduces direct cross-subsystem mutations in REPL.

Expected outcome:
- fewer side-effects in `Repl`
- clearer ownership of persistence and cross-crawl transitions

---

### Phase 5 — Prompt lifecycle normalization

Define a lightweight action result contract:
- `{ shouldPrompt: boolean }`
- optional `{ shouldExit: boolean }`

Centralize final prompting logic in one place, replacing ad-hoc `rl.prompt()` calls.

Expected outcome:
- eliminate prompt drift and forgotten prompt cases
- reduce repetitive branch endings

---

### Phase 6 — Hardening and acceptance

Run existing suites + new REPL-focused tests and validate:
- no CLI behavior regressions
- no state model regressions (`currentUrl`, cursor, stash)
- no persistence regressions (session sidecar/load)

## Measurable success criteria

1. `src/cli/repl.ts` reduced from 1856 lines to roughly 700–900 lines
2. Single shared navigation transaction path used by all navigation-producing actions
3. Prompt calls no longer duplicated across command branches
4. Existing test suites remain green
5. New targeted tests for extracted handlers/executors pass

## Execution strategy

Recommended implementation order:
1. Phase 0
2. Phase 1
3. Phase 2
4. Phase 3
5. Phase 5
6. Phase 4 (can be parallelized or deferred)
7. Phase 6

Rationale: maximize risk reduction early (navigation dedupe), then reduce branching, then improve ergonomics.

## Non-goals

- No UX redesign
- No command behavior changes
- No modifications to LLM prompt policy
- No changes to crawl/session data models unless required for extraction boundaries

## Bottom line

The current REPL is a strong implementation that has outgrown a single-file orchestration model. The highest-value move is a no-behavior-change extraction of shared navigation flow, then command and executor modularization with test-backed safety.
