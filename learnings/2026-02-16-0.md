# Architecture Review: Vision vs. Reality, and the Eight Decisions

## Where We Started

Phase 5 was committed. The codebase had grown organically across 5 phases and 3 days — from a mock-only demo spec to a real-website browser with HN extraction, form detection, goal tracking, and dual LLM providers. The TODO had 8 items. But the bigger question wasn't what to build next — it was whether the architecture matched the vision.

The trigger: `planAction()`. It exists in the LLM provider interface, is implemented in both providers, tested in the test file, and called from zero production code paths. Why? Because the REPL loop replaced it — the human makes every navigation decision by pressing a number. The function designed for agent autonomy was made redundant by human-in-the-loop design.

This led to a broader question: is Clawmium a context provider for external agents, or does it embed its own agent to process raw web content? The answer shapes everything.

## What We Actually Did

No code was written. This was a pure architecture and product alignment session — reviewing the original design spec against the current implementation, identifying where they diverged, and making explicit decisions about the project's direction.

### The Eight Decisions

We identified 8 key architectural and product decisions. Here's where we landed:

**1. Who is Clawmium for? → Layered. Agent-first, human-second.**

Agents interact with Clawmium the same way humans do — through CLI input/output. The human stays in the loop for auth (core design principle). The rendering layer (`/show`) exists because sometimes you need pixels — agent-first doesn't mean agent-only. The tagline still rings true.

**2. Where does intelligence live? → Inside, for now.**

The web is complex existing infrastructure. Clawmium needs its own intelligence to navigate it — interpreting pages, extracting data, structuring choices. Whether this intelligence eventually migrates to the calling agent is a future question. The current design — Clawmium's CLI I/O + generated context making it natural for agents to tool-use — is the right approach for now. This is debatable long-term but pragmatically correct today.

**3. What happens to `planAction`? → Wire it up behind `/auto`.**

Don't remove it (premature — the layered, agent-first design wants autonomous navigation). Don't redesign it (premature — we don't know if it works on real sites). Instead: add `/auto` mode as a spike. `interpret -> planAction -> execute` loop, human interrupts with Ctrl+C. Test on CityServe first. If the agent can navigate landing -> water bill -> detect login -> hand off -> extract data without pressing `1` at every step, `planAction` earns its place.

**4. Site-specific extractors? → Generic core, site quirks on demand.**

Core extraction/interpretation should be based on HTML standards — generic, works everywhere. Site-specific handling (like `sites/hn.ts`) exists as needed, on an as-needed basis. The analogy: browser extensions like Dark Reader. Generic transform with site-specific patches when a particular site's quirks demand it. This is already the pattern — just needs to be formalized.

**5. Navigation model? → Dedicated planning session.**

Stack-to-tree is a real architectural question with its own design document. Parked for a separate session. The linear stack works for now.

**6. How should Clawmium be consumed? → CLI + MCP.**

Two interfaces: human via CLI, agent via MCP server. Agent-first means MCP is first-class, not an afterthought. No HTTP API or library exports needed — CLI + MCP is sufficient.

**7. LLM provider strategy? → Agnostic, low priority.**

The principle is clear: no lock-in to any provider. But expanding/testing providers isn't the current priority. The interface is clean (`LLMProvider`), Anthropic parity gets fixed when it naturally comes up.

**8. What ships next? → Living TODO, evolved from discussion.**

The TODO is a living document that updates based on architectural decisions, not a static backlog.

## Top Learnings

1. **Dead code is a signal, not just debt.** `planAction()` being unused wasn't a cleanup task — it was evidence of an architectural fork the project hadn't consciously taken. "Why is this code never called?" is often a more important question than "should we delete it?"

2. **"Agent-first" has two meanings and you must pick one.** It can mean "agents consume this tool" (Clawmium as infrastructure) or "an agent drives this tool" (Clawmium as autonomous browser). The answer is both, layered — but without making that explicit, the code pulls in both directions simultaneously. The REPL is human-driven (meaning 1), the `planAction` interface is agent-driven (meaning 2), and neither knows which one is primary.

3. **The intelligence-location question is premature to resolve, correct to name.** Whether the LLM should live inside Clawmium or in the calling agent depends on how the web evolves. Today's web is complex enough that Clawmium needs its own intelligence. But the layered architecture (Decision 1) means this can migrate later without rewriting the browser engine layer. Naming the question prevents accidentally closing the door.

4. **Site-specific handling is browser extensions, not tech debt.** The instinct to feel bad about `sites/hn.ts` as a special case is wrong. Every real browser has site-specific behavior (compatibility quirks, extension overrides, content blockers with site rules). The pattern is: generic standard-based core, site-specific patches when reality demands them. Making this a conscious pattern (registry, on-demand activation) rather than ad-hoc `if` statements is the improvement needed.

5. **MCP follows from "agent-first" automatically.** Once you say "agents interact with Clawmium the same way humans do — through I/O," the next question is "what's the agent's I/O interface?" For humans it's the CLI REPL. For agents it's MCP tools. Same capabilities, different wire format. This should have been obvious from the tagline but wasn't designed in from the start.

6. **Alignment sessions produce more value per hour than feature sessions.** Three days of building produced a working browser and 8 open architectural questions. One alignment session resolved 7 of them and reframed the TODO. The ratio of decisions-per-hour is much higher in a review session than in a build session. Building without alignment accumulates decisions-as-debt.
