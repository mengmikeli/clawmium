# Crawls Design Review: GoalContext, LLM Judgment, and Three Principles

## Where We Started

The architecture alignment session (`2026-02-16-0.md`) parked Decision 5 (navigation model) for a dedicated session with a design document. That document — "Crawls: Tree-Structured Navigation Context for Clawmium" — proposed a three-layer architecture:

- **Layer 1:** REPL stack (physical position, unchanged)
- **Layer 2:** Crawl tree (mechanical observer of navigation events, new)
- **Layer 3:** LLM-managed reorganization (semantic, future)

The design was thorough: `CrawlNode` and `Crawl` interfaces, URL deduplication, first-discovery-path as canonical tree edge, project vs scratch modes, burst detection for auto-project creation, markdown persistence, a 4-phase build plan, and explicit future-proofing for Layer 3 with `detachSubtree`/`attachSubtree`.

This session reviewed the design, identified tensions, and refined it through two key insights.

## What We Discussed

### Design Review: Six Pushback Points

The initial review raised six concerns with the original design:

1. **GoalContext ↔ Crawl overlap.** `GoalContext.breadcrumb` (a flat, 3-element sliding window) tracks the same information the crawl tree captures more richly. Two breadcrumb systems would coexist without a convergence plan.

2. **`nodeIndex: Map<string, CrawlNode>` doesn't survive persistence.** Maps don't serialize. Needs to be explicitly documented as a runtime cache rebuilt on load.

3. **`/goto` same domain creates misleading parent-child edges.** Jumping directly to an unrelated page on the same domain makes it a child of the current page, implying a relationship that doesn't exist.

4. **Burst detection (3 URLs in 30s) is a premature heuristic.** Adds complexity (timestamp tracking, retroactive scratch-to-project migration), calibrated against usage patterns we haven't observed.

5. **Project vs scratch boundary management.** Two explicit modes with different code paths, storage, and structure. The boundary between them (when does scratch become a project?) has hidden complexity.

6. **Per-node conversation capture needs scoping.** Follow-up questions should be recorded on CrawlNodes, but the current REPL stores conversation in a flat `state.history` array. Two write targets need coordination.

### Key Insight 1: GoalContext Drives Crawl Lifecycle

The pivotal realization: `GoalContext` is not a Playwright concept or an external dependency — it's Clawmium's own invention (`src/llm/provider.ts`, `src/cli/goals.ts`), a Phase 5 addition that replaced a flat `userGoal` string. It tracks intent: what's the user's overall goal (`baseGoal`), what are they currently focused on (`activeIntent`), and where have they been (`breadcrumb`).

The relationship between GoalContext and the crawl tree isn't overlap — it's a loop:

```
GoalContext = intent (why am I browsing, what am I looking for)
    ↓ drives
Crawl tree  = structure (what did I find, how did I get there)
    ↓ feeds back into
GoalContext = enriched context for LLM prompts (intent + path + history)
```

GoalContext provides the **intent signal** that answers the crawl layer's lifecycle questions: when to create a new tree, what to name the root, whether two navigations belong to the same crawl. The crawl tree provides the **structural context** that enriches GoalContext beyond a 3-element sliding window.

This resolved concerns 1 (not overlap, but a feedback loop), 4 (burst detection replaced by intent signal), and 5 (project/scratch distinction becomes an LLM judgment about a crawl's coherence, not a mode flag).

### Key Insight 2: Three Principles

Rather than resolving remaining design questions with more heuristics, we established three principles:

**Principle 1: Don't hardcode rules. Trust the LLM to make judgment calls.**

Every question that involves semantic judgment — "does this page belong to the active crawl?", "what should this crawl be named?", "is this a context switch?" — goes to the LLM, not to hardcoded thresholds or pattern matching. The mechanical layer records facts. The LLM interprets them.

This eliminates:
- Burst detection (timer heuristic → LLM judges intent continuity)
- Project/scratch mode (explicit flag → LLM assesses coherence when asked)
- Edge classification rules (hardcoded link-vs-jump → mechanical fact recorded, LLM interprets when needed)
- Crawl naming rules (auto-name from baseGoal → LLM names once it has context)

**Principle 2: Core mechanism should be simple and work as intended.**

The crawl tree's mechanical layer has four operations: create node, find node (dedup), attach to parent, store metadata. Everything else is annotation or LLM judgment on top. This mirrors the REPL stack: push, pop, peek — no decision-making in the data structure itself.

**Principle 3: We can always refactor if we follow 1 and 2 carefully.**

Simple mechanical infrastructure + LLM-based semantic processing = a system where the parts that are hard to change (data structures, persistence format) are simple and stable, and the parts that need iteration (judgment calls, naming, organization) are soft and prompt-driven.

### Resulting Design Changes

**Data model:**
- Drop `mode: 'project' | 'scratch'` from `Crawl`. All crawls are structurally identical.
- Drop burst detection entirely. Crawl lifecycle is LLM-driven via GoalContext.
- Add `parentId: string | null` to `CrawlNode`. Makes ancestor traversal O(depth) instead of O(n). Important now that the tree feeds context back into LLM prompts.
- Add `reachedBy: 'choice' | 'goto' | 'back' | 'forward' | 'auto'` to `CrawlNode`. Record the mechanical fact of how navigation happened. Don't interpret it — let the LLM interpret when needed.
- `nodeIndex` explicitly documented as runtime cache, rebuilt from tree on load.

**Phase plan:**

| Phase | Scope |
|-------|-------|
| **Phase 1** | Data structures + tree operations + persistence. `CrawlNode`, `Crawl`, `CrawlManager`. Create, find, attach, detach, ancestors, display. Save/load markdown. All mechanical, testable without LLM or browser. |
| **Phase 2a** | Hook `addNavigation()` into REPL navigation paths. Passive recording. Every navigation creates/finds a node. Single crawl auto-created on first navigation, timestamp-named. |
| **Phase 2b** | `/tree` command for display. Minimal CLI surface. |
| **Phase 3** | LLM integration. Lifecycle decisions ("extend current crawl or start new one?"). LLM-driven naming. Crawl ancestor context fed into `interpret()` calls. GoalContext breadcrumb derived from tree. |
| **Phase 4** | Polish. `/crawl` commands (rename, end, list, load). Display refinements. |

**Explicitly deferred (unchanged):**
- Layer 3 drift pruning
- Cross-session context injection
- Convergence detection (merging related crawls)
- Crawl search

## Top Learnings

1. **Intent and structure are a feedback loop, not competing systems.** GoalContext (intent) and crawl tree (structure) looked like overlapping responsibilities. They're actually two halves of a cycle: intent drives structure creation, structure enriches intent for better LLM context. Recognizing the loop eliminated the "which one is primary?" question — both are, at different points in the cycle.

2. **"Don't hardcode rules" is a concrete engineering principle, not just a platitude.** Applied systematically, it eliminated burst detection, project/scratch mode, edge classification rules, and naming heuristics — all replaced by "record the mechanical fact, let the LLM judge." This isn't laziness; it's recognizing which layer should own which decisions. The mechanical layer owns structure. The LLM owns meaning.

3. **Simple infra + LLM semantics = safe refactoring.** When the hard-to-change parts (data structures, persistence) are simple, and the easy-to-change parts (judgments, naming, organization) are prompt-driven, the system is naturally refactor-friendly. You never need to rewrite the tree to change how the LLM interprets it. This is the same pattern that made the REPL stack stable: dumb data structure + smart LLM on top.

4. **Record facts, defer interpretation.** `reachedBy: 'goto'` is a fact. "This was a context switch" is an interpretation. Store the fact in the mechanical layer, let the LLM produce the interpretation when needed. Facts are cheap to store, stable over time, and don't need to be re-evaluated. Interpretations are expensive, context-dependent, and improve as prompts improve.

5. **Design reviews that surface feedback loops are more valuable than design reviews that surface missing fields.** Adding `parentId` and `reachedBy` to `CrawlNode` improves the design incrementally. Discovering that GoalContext and the crawl tree form a feedback loop changes how the entire system is conceived. The structural insight is worth 10x the field-level improvements.
