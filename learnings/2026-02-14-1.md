# Rewriting the Spec to Match the Ship

## Where We Started

CLAUD.md was still the pre-implementation design spec from February 13. It described what we *planned* to build: `chalk` + `ora` + `@inquirer/prompts` for CLI, Option A (minimized headed window) for show/hide, mock-only site support, prompts focused on navigation. Meanwhile, the actual codebase had diverged across two full build sessions — real website support, raw ANSI terminal output, headless-first with cookie transfer, content-first prompts, REPL stack refactor with `syncBrowser()`, new commands (`/forward`, `/home`, `/refresh`, `/url`).

The learnings files (`2026-02-13-1.md`, `2026-02-14-0.md`) documented what happened, but CLAUD.md — the file LLMs read first — still described a system that no longer existed.

## What We Actually Did

Rewrote CLAUD.md from design spec to implementation reference. Not a patch — a near-complete replacement. The diff was ~480 lines removed, ~325 lines added.

## What Went Wrong

Nothing broke — this was a documentation task. But the *delay* in updating was itself the problem:

- **Two sessions of drift.** The spec was written before any code existed. After two sessions of building, debugging, and refactoring, it described a different system than the one running. Anyone (human or LLM) reading CLAUD.md first would form wrong mental models about how the code works.
- **Learnings files aren't the spec.** `2026-02-13-1.md` and `2026-02-14-0.md` captured what happened and what we learned, but they're narrative — not reference. An LLM asked to "add a new command" would read CLAUD.md for the command table and miss `2026-02-14-0.md` where `/forward` was introduced.

## Top Learnings

1. **The spec is a living document or it's a historical artifact.** A pre-implementation spec that doesn't get updated becomes misleading. The learnings preserved in `2026-02-13-0.md` (the original) stay valuable as history; CLAUD.md must reflect current reality.

2. **Delete what's done, keep what's current.** Build phases, implementation option comparisons, and scripted demo transcripts served their purpose during planning. Once the code exists, they're noise that obscures the actual architecture. The original lives in `learnings/2026-02-13-0.md` for anyone who wants the history.

3. **Reference docs should match the code's vocabulary.** The old spec said `isAlive()` and `recover()`. The code now says `syncBrowser()` and `recoverBrowser()`. If the spec uses old names, every LLM session starts with a wrong map. Renaming in docs costs nothing; debugging with a stale mental model costs sessions.

4. **Update the spec on the same day you refactor.** The REPL stack refactor (2026-02-14-0) introduced `currentUrl`, `syncBrowser()`, `/forward`, `/home`, `/refresh`, `/url` — and none of these appeared in CLAUD.md until this separate pass. Ideally, the spec update is part of the refactor, not a follow-up task.

5. **Learnings and specs serve different audiences.** Learnings are for future-you understanding *why* decisions were made and what traps to avoid. The spec (CLAUD.md) is for *right now* — an LLM or developer dropping into the codebase cold. Both are necessary; neither replaces the other.
