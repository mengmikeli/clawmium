# `/auto --max-steps` — configurable step limit

Date: 2026-02-18
Scope: `src/cli/handlers/session.ts`, `src/cli/repl.ts`, `src/cli/handler-types.ts`, `src/__test__repl.ts`, `.env.example`, `CLAUDE.md`

## What was built

- **Flag parsing**: `--max-steps N` / `-s N` parsed via regex in `handleAuto()` (`handlers/session.ts`). Flag text stripped from goal string. Invalid values (non-integer, out of 1–100 range) show error and abort without starting auto mode.
- **Env reading**: `AUTO_MAX_STEPS` read in `runAutoMode()` (`repl.ts`) with the same integer + bounds validation. Invalid env values trigger a warning and fall through.
- **Precedence chain**: CLI flag > `.env` > hardcoded default (10). Implemented as `maxStepsOverride ?? envSteps` — the handler passes `undefined` when no flag is given, letting the env layer have its say.
- **Type update**: `ReplContext.runAutoMode` signature changed from `(goal: string) => Promise<void>` to `(goal: string, maxSteps?: number) => Promise<void>`.
- **7 new tests** (10 new assertions), 53 total in `test:repl`, 534 total across 7 suites, 0 failures.
- **Docs**: `.env.example` updated with `AUTO_MAX_STEPS=10` entry. CLAUDE.md updated with `.env` block, CLI table, and design history.

## Learnings

### 1. Plan-to-implementation for well-scoped features

This was a textbook "well-scoped feature" — clear requirements, known integration points, bounded blast radius. The plan took ~5 minutes to write and was 90% accurate. The 10% delta (inlined function, flat parameter) improved the implementation without changing the architecture. For features this size, the plan's main value isn't catching surprises — it's giving the implementer confidence to move fast.

### 2. Regex flag parsing: simple but has edge cases

The flag regex `(?:--max-steps|-s)\s+(\S+)` handles the common cases cleanly. The goal text recovery (`arg.replace(flagRegex, "").trim()`) works because the flag is always `--max-steps N` or `-s N` — a fixed pattern that doesn't overlap with goal text. Edge case discovered during testing: `/auto --max-steps 5` with no goal text — the flag gets parsed correctly but goal is empty, which the existing empty-goal guard catches. This is why testing edge cases matters even for "trivial" parsing.

### 3. The handler extraction (Phase 2) paid off immediately

This was the first feature added *after* the Phase 2 REPL refactor. The change to `handleAuto()` was entirely within `handlers/session.ts` — no need to touch the 1596-line `repl.ts` switch/case or worry about disrupting other commands. The `ReplContext.runAutoMode` type change propagated cleanly through `handler-types.ts` → `repl.ts buildContext()`. This is exactly the modularity the refactor was designed to enable. Total time from plan to passing tests: under 30 minutes.

### 4. Precedence chains are a recurring pattern

This project now has four precedence chains:

| Feature | Chain |
|---------|-------|
| `tokenLimit()` | env var → hardcoded default |
| Session resume | JSON sidecar → markdown fallback |
| Page load | networkidle → domcontentloaded → continue |
| `/auto` maxSteps | CLI flag → env var → hardcoded default |

The pattern: highest-specificity source wins, each layer validates independently, invalid values fall through silently (with optional warning). The `/auto` chain adds a new first layer (CLI flag) on top of the two-layer pattern used by `tokenLimit()`. If a fifth precedence chain appears, it would be worth extracting a generic `resolveConfig(sources: Array<() => number | undefined>, fallback: number)` helper. For now, inline is clearer.

### 5. Test mock pattern: spy-via-replacement

The new tests override `repl.runAutoMode` directly via cast-to-any, capturing args:

```typescript
let capturedGoal = "";
let capturedMaxSteps: number | undefined = -1;
(repl as any).runAutoMode = async (goal: string, maxSteps?: number) => {
  capturedGoal = goal;
  capturedMaxSteps = maxSteps;
};
```

This "spy" pattern works cleanly because the tests don't need to verify what `runAutoMode` does internally — just that the handler dispatches correctly with the right arguments. Separation of concerns: handler tests verify flag parsing and dispatch; runner tests (in `test:auto`) verify the autonomous loop itself.

## Top takeaway

**Handler extraction enables incremental feature work.** The Phase 2 REPL refactor (command handlers) was justified primarily as a structural improvement — reducing the monolith, making coupling explicit. But its immediate practical benefit was enabling this feature in under 30 minutes with changes confined to 3 small files. The old monolith would have required editing a 2134-line switch/case and running the full test suite nervously. Instead, `handleAuto()` in `session.ts` is 22 lines, the type change propagated mechanically, and the tests target the exact handler behavior. Structural refactors pay for themselves not in the refactoring session, but in the next feature after.
