# Architecture Alignment — Clawmium and the Agentic Web Infrastructure Stack

## Where We Started

Six days since the last architecture alignment session (2026-02-16, "Eight Decisions"). Since then: REPL refactor completed (Phases 0–2), `/auto` mode shipped with configurable step limits, session persistence and crawl stash are stable. 534 test assertions across 7 suites. The infrastructure layer is solid.

The trigger for this session: the agentic web infrastructure stack is crystallizing in the open-source ecosystem. Vercel's agent-browser hit 15k+ stars. Cloudflare announced `Accept: text/markdown` for LLM-friendly content delivery. Playwright's `ariaSnapshot()` is becoming the standard for semantic page extraction. The question: where does Clawmium fit in this landscape, and what should it adopt vs. reject?

## The Landscape

### Three-Layer Stack

The agentic web infrastructure is organizing into three layers:

| Layer | What it does | Key players |
|-------|-------------|-------------|
| **Content** | Convert web pages to LLM-friendly formats | Cloudflare (markdown), Jina, Firecrawl |
| **Compute** | Orchestrate LLM calls and tool use | Vercel AI SDK, LangChain |
| **Navigation** | Control browsers for agents | agent-browser, Browser Use, Stagehand |

### agent-browser Deep Dive

Vercel's agent-browser is the navigation-layer standard:
- Pure pipe architecture — external LLM drives all decisions
- `ariaSnapshot()` for semantic page structure with `@ref` identifiers
- `--profile <path>` for persistent browser profiles
- `state save/load` for session snapshots
- No semantic navigation history, no crawl memory, no internal intelligence

Key insight: agent-browser is infrastructure. Clawmium is a product. They operate at different levels of abstraction. Clawmium could theoretically *use* agent-browser as its browser layer — but its value comes from what it builds *on top* of browser control.

### Where Clawmium Sits

Clawmium spans navigation + compute, with a unique **memory layer** (crawl tree) that nothing else has. The crawl tree — a persistent graph of markdown files with LLM-curated summaries at each node — is the differentiator. Internal LLM intelligence exists to *produce* those markdown artifacts, not as an end in itself.

## Seven Decisions

### Decision 1: Adopt accessibility tree as parallel extraction mode

**Resolution: Yes — parallel, not replacement.**

Add Playwright's `ariaSnapshot()` as a second extraction path alongside the DOM text dump. The two serve different purposes:
- **DOM text** → content-first understanding ("what the page says") → feeds summaries, content boxes
- **A11y tree** → semantic structure with stable `@ref` identifiers → feeds element targeting, choice references

Choices would reference `@ref` identifiers instead of CSS selectors — more reliable across page updates, shorter tokens for LLM context. This is the single highest-impact extraction improvement.

### Decision 2: Intelligence stays inside — crawl artifacts are the MCP interface

**Resolution: Internal LLM is necessary because it produces the crawl artifacts. MCP exposes the file tree.**

The critical insight: Clawmium's MCP interface should be its **crawl artifact tree on the filesystem** — a tree/graph of markdown files that external agents can read directly. Not an API that returns JSON. Not a pipe to raw page content.

This is why internal LLM interpretation is needed: someone has to convert raw web pages into curated markdown. agent-browser is a pure pipe — the external LLM does all interpretation. Clawmium does interpretation internally so it can produce persistent, navigable knowledge artifacts.

The MCP server, when built, exposes:
- The crawl artifact filesystem tree (markdown files with summaries, links, metadata)
- Navigation commands (browse, back, follow) that produce new artifacts
- The crawl tree structure itself (which pages link to which, how they were reached)

External agents don't need to understand HTML or run LLMs against raw content — they read Clawmium's curated markdown.

### Decision 3: Auth persistence via `storageState()` — needs architecture session

**Resolution: Direction confirmed. Needs dedicated design session before implementation.**

The shape is clear:
- `~/clm/profiles/{hostname}.json` via Playwright's `storageState()`
- Auto-load on startup for known sites
- Save after successful CLI auth handoff

But the details need thought:
- How does this interact with session resume? (Session already has cookie state via browser context)
- Profile per hostname vs. per origin vs. per site group?
- Expiry and refresh — when do stored cookies go stale?
- Security model — these are credential-equivalent files
- Integration with `/show`/`/hide` cookie transfer (currently per-session, not persisted)

Parking for a dedicated architecture session. This is "most impactful near-term addition" per the synthesis but needs careful design, not a quick implementation.

### Decision 4: Add `Accept: text/markdown` header

**Resolution: Yes, implement. Trivial code change, large quality improvement.**

Cloudflare sites return clean markdown directly when requested. Implementation:
- Add `Accept: text/markdown, text/html;q=0.9` to Playwright request headers
- Check response content-type — if `text/markdown`, use directly (skip DOM extraction entirely)
- Fallback to DOM extraction for non-supporting sites
- Complements the a11y tree: markdown for content understanding, a11y tree for interaction

Maybe 20 lines of code. The content pipeline becomes: markdown-first (if server supports it) → DOM text (standard path) → network JSON (SPA fallback).

### Decision 5: The crawl tree is Clawmium's moat

**Resolution: Strategic position confirmed. No action needed beyond continued investment.**

What Clawmium has that nothing else does:
- **Navigational memory** with cached LLM interpretations at each node
- **Cross-domain stash** with instant `/back` without re-fetch
- **Tree-derived breadcrumbs** that improve LLM context over time
- **Session persistence** and resume across launches
- **Human-in-the-loop auth** — the agent handles everything except credentials

The crawl tree's evolution into persistent markdown artifact folders is the path to the MCP vision (Decision 2). The crawl tree isn't just a feature — it's the architectural foundation for Clawmium's role in the agentic web stack.

### Decision 6: Site quirks as domain-specific skill files

**Resolution: Reframe from "code registry" to "site skill files" — analogous to `.claude/skills/SKILL.md`.**

The current `sites/hn.ts` is hardcoded TypeScript. The better model: domain-specific skill files that describe how to handle a particular site's quirks. Like how `.claude/skills/daily-reflection/SKILL.md` teaches Claude Code a workflow, site skill files would teach Clawmium how to handle HN comments, NYT paywalls, Reddit thread nesting, etc.

This reframing has implications:
- Site knowledge becomes declarative (markdown/config) rather than imperative (TypeScript)
- LLM can read the skill file and adapt its extraction/interpretation accordingly
- Users could contribute site skills without writing code
- The a11y tree may reduce which sites *need* skill files (good semantic HTML needs no special handling)

Implementation deferred until after a11y tree adoption — the scope of needed quirks will change.

### Decision 7: Priority roadmap

**Resolution: Confirmed order.**

1. **[high]** A11y tree extraction — `ariaSnapshot()` as parallel content source, `@ref` in choices
2. **[high]** `Accept: text/markdown` header — use markdown when available, DOM fallback
3. **[high]** Auth persistence — dedicated architecture session, then implementation
4. **[medium]** MCP server design — crawl artifacts as filesystem interface
5. **[medium]** Persistent crawl artifacts — markdown folder structure (prerequisite for MCP vision)
6. **[low]** Site skill files — formalize after a11y tree changes the scope

## Top Learnings

1. **Infrastructure vs. product is the key distinction.** agent-browser is infrastructure (pure pipe, external intelligence). Clawmium is a product (embedded intelligence, curated output). They don't compete — they operate at different abstraction levels. Clawmium could use agent-browser-style primitives internally while adding its own intelligence layer on top.

2. **The crawl artifact tree IS the MCP interface.** The realization that MCP should expose a filesystem of curated markdown — not an API returning JSON — clarifies both the MCP design and the crawl persistence roadmap. Persistent crawl artifacts aren't just a "nice to have" storage format; they're the foundation for Clawmium's programmatic interface.

3. **Internal LLM interpretation justifies itself through artifacts.** The question "why does Clawmium need its own LLM?" has a clear answer: because someone has to produce the curated markdown that external agents consume. A pure pipe doesn't produce persistent knowledge. The interpretation layer exists to create the crawl artifact tree.

4. **Site quirks are skills, not code.** Reframing `sites/hn.ts` from "site-specific extractor code" to "domain skill file" (like SKILL.md) changes the extensibility model. Declarative site knowledge that the LLM reads and applies is more powerful and more accessible than hardcoded TypeScript parsers.

5. **`Accept: text/markdown` is a free lunch.** Trivial implementation, significant quality improvement for supported sites, and it fits perfectly into the existing content pipeline. The web is actively becoming more LLM-friendly — Clawmium should adopt these standards as they emerge.

6. **Auth persistence needs architecture, not just implementation.** The instinct to "just add `storageState()`" underestimates the design surface: interaction with session resume, security model, profile scoping, cookie expiry. Worth a dedicated session rather than a quick hack.
