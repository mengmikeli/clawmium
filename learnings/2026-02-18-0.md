# REPL Refactor — Phases 0, 1, 2: Reflection

Date: 2026-02-18
Scope: `src/cli/repl.ts`, `src/cli/handler-types.ts`, `src/cli/handlers/`, `src/__test__repl.ts`

## What was built

Three phases of the REPL refactor plan (from `learnings/2026-02-17-4.md`), executed in a single session:

1. **Phase 0 — Safety net tests** (`src/__test__repl.ts`, 43 assertions). Mock factories for Page, Engine, Navigator, LLM, Interceptor, readline. Covers `/goto` (8 tests), `/home` (6), `/back`+`/forward` (6), numbered choices (4), navigation invariants (4), other commands (4). No test framework — follows `__test__auto.ts` pattern.

2. **Phase 1 — `navigateAndProcess()` extraction** (30-line private method). Owns the 8-step navigation transaction: syncBrowser → truncateCursorForward → interceptor.clear → pendingReachedBy → preNavigate hook → nav.goto (try/catch) → currentUrl → settle → processCurrentPage. Migrated `/demo`, `/home` (2 paths), `/goto`. Eliminated ~40 lines of duplicated code.

3. **Phase 2 — Command handler extraction** (4 new files, 689 lines total). `handler-types.ts` (95 lines): `SessionState`, `ReplContext`, `CommandHandler`, `HandlerResult`. Three handler files: `handlers/navigation.ts` (226 lines, 8 commands), `handlers/session.ts` (105 lines, 7 commands), `handlers/crawl.ts` (263 lines, 4 commands with subcommands). Dispatch map + `buildContext()` in repl.ts. `handleInput()` is now a 10-line router for slash commands.

### What the plan proposed vs what we built

**Directory structure.** The plan proposed `src/cli/commands/`. We used `src/cli/handlers/`. Trivial naming difference — `handlers` is more accurate since these aren't self-contained commands, they're handler functions that receive a context bag.

**Handler grouping.** The plan proposed 4 files (navigation, session, crawl, system). We used 3 files (navigation, session, crawl) — merging `system` into `session` since `/help`, `/url`, `/login` are lightweight and splitting further would create a file with only 3 tiny functions.

**`ReplContext` surface area.** The plan predicted ~30 operations. The actual `ReplContext` has 22 bound methods plus 8 direct field accesses. Slightly smaller than feared, which is good. The plan correctly noted this is "transitional — better than passing the Repl instance."

**Migration order.** The plan proposed 13 incremental steps for Phase 2. We executed it in a single batch: create all types + all 3 handler files, then replace the entire switch/case body in one edit. This was faster but riskier. The safety net tests (Phase 0) justified the batch approach — we had 43 assertions validating every important command path.

**Phase 1 `preNavigate` hook.** The plan didn't specify the `preNavigate` callback pattern. During implementation, `/home` needed to reset goalContext *before* navigation but *after* cursor truncation. The `opts.preNavigate` hook emerged as the natural seam. This is the kind of design detail that reveals itself during implementation, not planning.

## Learnings

### 1. Mocking Playwright's Page object requires surgical precision

The mock `page.evaluate()` is the hardest mock in the system. Three different callers (`detectLoginPage`, `detectInteractiveForms`, `syncBrowser`) pass different anonymous functions to `evaluate()`, and each expects a different return type (`boolean`, `DetectedForm[]`, `string`). Our mock inspects `fn.toString()` to dispatch:

```typescript
if (fnStr.includes("location.href")) return currentUrl;  // syncBrowser
if (fnStr.includes("results") && fnStr.includes("querySelectorAll")) return [];  // forms
return false;  // login detection
```

This is brittle — any refactor of the evaluate callbacks could break the mock. But it's the pragmatic choice when you can't easily inject stubs into third-party detection functions that call `page.evaluate()` internally.

**Takeaway:** The mock fragility is a signal that `detectLoginPage()` and `detectInteractiveForms()` should accept extracted page data, not the raw Page object. That's a future refactor — but the test suite will catch the breakage when it happens, which is exactly the point of Phase 0.

### 2. Safety net tests as batch-change insurance

The plan's original Phase 2 migration order (13 incremental steps) was designed for a world without good test coverage. With 43 assertions from Phase 0, we could move all 19 command branches in a single edit and verify immediately. The safety net didn't just prevent regressions — it changed the viable migration strategy from incremental to batch.

**Pattern:** When you're about to do N incremental refactoring steps, ask whether a test harness would let you do it in 1 step instead. If the test suite takes 2 seconds to run and gives high coverage of the affected paths, batch wins.

### 3. `HandlerResult` is simpler than predicted

The plan envisioned handlers needing `{ promptHandled: true }` for `/quit` and `/login`. In practice, only `/quit` and `/login` use it — exactly as predicted. But the prediction that this would "eliminate 40+ duplicate `rl.prompt()` calls" was accurate: prompt calls went from 58 → 15.

The remaining 15 are in:
- `handleInput()` dispatcher (1 for handler, 1 for unknown command)
- Line handler error paths (3)
- SIGINT handler (1)
- Choice execution branches (5 — show, fill, anchor skip, navigate, stale)
- Free text (1)
- `startReadline()` initial prompt (1)
- `runLoginFlow()` (2)

These are structurally correct — they're in the REPL core, not in command handlers. Phase 5 of the original plan (prompt lifecycle normalization) would address some of these, but the current distribution is already much cleaner.

### 4. The `ReplContext` bag is honest about coupling

`buildContext()` binds 22 methods from `Repl` into the context object. This looks like a lot, but it's *honest* coupling — previously, these same dependencies existed but were hidden behind `this.` references inside a 2134-line monolith. Making them explicit reveals which handlers need which operations:

- **Navigation handlers** (`/goto`, `/back`, `/forward`, `/home`, `/demo`): heaviest users — `navigateAndProcess`, `restoreFromNode`, `stashCrawl`, `saveSessionSidecar`, `ensureCityServe`
- **Session handlers** (`/save`, `/quit`, `/clear`): moderate — `forceSave`, `shutdown`, `clearRepl`, `clearCrawl`, `clearBrowser`, `confirmAction`
- **Crawl handlers** (`/tree`, `/stack`, `/history`, `/crawl`): lightest — mostly read from `crawlManager`, only `/crawl load` needs `stashCrawl` and `setInterpretation`

This gradient suggests that Phases 3-4 (non-command executors + session coordination boundary) would reduce the heaviest handlers further by extracting `restoreFromNode` and stash orchestration into their own modules.

### 5. The plan's execution order recommendation was correct

The original plan recommended: Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 5 → Phase 4 → Phase 6. We executed 0 → 1 → 2 and confirmed the ordering was right:

- Phase 0 (tests) had to come first — it enabled the batch Phase 2 migration.
- Phase 1 (navigateAndProcess) had to come before Phase 2 — handlers call `ctx.navigateAndProcess()`, which wouldn't exist yet if we'd done Phase 2 first.
- Phase 2 (handlers) logically follows because it relies on Phase 1's shared method.

The plan also said "Phase 4 can be parallelized or deferred." With the handlers now extracted, Phase 4 (session/crawl coordination) becomes *easier* because the operations to coordinate are visible in `ReplContext` rather than buried in switch/case branches.

### 6. What the original plan got wrong

**Line count prediction.** The plan predicted "reduce to ~1450 lines" for Phases 0-2. We hit 1596 — 146 lines over. The difference is `buildContext()` (45 lines of method bindings) and the dispatch map (20 lines), neither of which was accounted for. The plan also underestimated that `navigateAndProcess()` (30 lines) adds lines while only removing ~40, for a net reduction of ~10 rather than the imagined "~40 lines removed."

**Handler file sizes.** The plan predicted `~300 lines` for navigation, `~200 lines` for session, `~250 lines` for crawl. Actual: 226, 105, 263. Session was much smaller than predicted because many "session" commands (`/save`, `/url`, `/help`) are trivially short. Navigation was smaller because `navigateAndProcess()` absorbed the bulk of the navigation logic.

**These errors don't matter.** The plan's value was the architecture (dispatch map, context bag, handler files), not the line counts. Getting the direction right and the details approximately right is what plans should do.

## Top takeaway

**Plans should be right about architecture and approximate about metrics.** The 2026-02-17-4 plan nailed the architecture: dispatch map, context bag, handler files, navigation transaction extraction. It was ~10% off on line counts, wrong about file sizes, and proposed 13 incremental steps where 1 batch step sufficed. None of that mattered. The plan's value was giving us confidence to make a large structural change safely, and the safety net tests (Phase 0) turned out to be the highest-leverage investment — they upgraded the migration strategy from "13 careful steps" to "1 confident batch."
